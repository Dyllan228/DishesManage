## D-001 · 2026-10-15 · 锁定 §12 全部开放问题

**状态**：已决议

**背景**：需求设计文档 v1.0 遗留 6 个开放问题，阻塞 M1 开工。用户授权由开发方全权决策。

**决议**：

### Q1 份量换算 / 非可分割单位
采用**双场景分离**策略，替代文档原 R7 的「一律保留小数」：

| 场景 | 处理 | 例（1 个鸡蛋 × 1.5） |
|---|---|---|
| 菜谱详情展示 | 保留精算值 + 提示 | `1.5 个`（提示：约 2 个） |
| 备菜/采购清单 | 向上取整 | `2 个` |

理由：做菜按比例算才不破坏配方，买菜必须整数。原 R7 方案在采购场景不成立——没人能买 1.5 个鸡蛋。

落地：单位字典加 `divisible: boolean` / `roundMode: 'ceil' | 'exact'`；`src/domain/scale.ts` 按场景选择舍入。

### Q2 食材别名字典
**内置约 200 条基础字典**，外置为 JSON（`src/data/ingredientDict.json`），用户可增删改，随数据一起导入导出。

理由：备菜清单能否正确合并去重完全依赖别名归一化。若空白起步，产品最核心的价值（「点 3 道菜自动出合并清单」）开箱即错。这是产品的立足点，不能交给用户从零积累。

### Q3 分类树
**菜系从分类树移除，降级为标签维度。**

原方案把「川菜/粤菜/湘菜」放在 `家常菜` 下作为二级分类，问题是一道「回锅肉」既是川菜又是荤菜，放进唯一归属的分类树必然二义，用户会纠结「这菜到底该放哪」。

- 分类树一级**只按上菜类型**：家常菜 / 荤菜 / 素菜 / 汤羹 / 主食 / 凉菜 / 早餐 / 甜品烘焙 / 饮品 / 未分类
- 新增标签维度 **「菜系」**：川菜/粤菜/鲁菜/湘菜/江浙菜/东北菜/西北菜/云贵菜/西餐/日韩/东南亚

这样唯一归属无歧义，交叉属性全部交给多对多的标签。

### Q4 多菜并行时间线
**列入本期，但只做最小形态**：按「前置耗时最长者先动」给出开火顺序 + 每道菜的关键时间点。**不做**甘特图式自动排程。

理由：这是差异化亮点值得验证，但复杂排程算法投入产出比未经验证。先用最小形态确认它是否真的有用，再决定是否加码。

### Q5 打印菜谱
**本期不做**，留 Backlog。导出图片 / 复制文本已覆盖分享给家人的场景，打印是低频桌面需求。

### Q6 部署
- 开发：Vite dev server（localhost 下 PWA/Service Worker 可用，不需要 HTTPS）
- 交付：Vercel / Netlify 静态托管（自带 HTTPS）
- **不做**内网自签证书方案；本项目无后端，纯静态托管零成本

**影响范围**：需求文档 §4.2.4（分类树重画）、§5.2（tags.dimension 增加 cuisine）、§12（改为决议记录）、R7（风险关闭）；文档版本升至 v1.1。

## D-003 · 2026-10-15 · 备菜清单用一张表同时承载派生数据与用户状态

**状态**：已决议（影响文档 §5.2）

**背景**：文档 §5.2 设计的是 `shoppingLists` + `shoppingItems` 两张表。实际实现时发现一个矛盾：
清单内容是**派生数据**（由今日菜单实时算出，菜单一变就该重算），但用户的勾选、库存标记
（FR-3.14 / FR-3.15）**必须持久化**且不能被重算冲掉。

**决议**：合并为一张 `shoppingItems` 表，靠确定性主键解决：

- 派生行：`id = ${date}|${itemKey}`，`itemKey = 归一化id|单位`。重算时按 `itemKey` 匹配旧行，
  **只刷新内容字段**（名称/用量/来源），保留 `checked` / `stockStatus`
- 手动追加行（FR-3.19）：`isManual = true`，重算时整行原样保留，永不被覆盖
- 菜单里被移除的菜，对应食材行在重算时自动清理（除非是手动项）

**理由**：两表方案需要额外维护 listId 的关联与生命周期，而这里天然只有「今天一张清单」。
单表 + 确定性键更简单，且免费获得 upsert 语义。`itemKey` 也成了跨重算匹配勾选状态的稳定锚点。

**副作用**：文档 §5.2 的 `shoppingLists` 表不实现。

## D-004 · 2026-10-15 · 食材用量输入合并为一个自由文本框

**状态**：已决议（对 FR-1.2 / FR-1.3 的实现方式微调）

**背景**：FR-1.2 要求食材行是「名称 + 用量 + 单位 + 备注」四段式，FR-1.3 要求单位提供候选。
严格按四段式做会得到两个输入框（数字 + 单位），但录入时用户手上拿到的原文往往是
「500g」「2 个」「适量」「两把」这种混合形态，拆成两个框反而更慢、还要在脑子里分离。

**决议**：用量做成**一个自由文本框** `amountRaw`，挂 `datalist` 提供单位候选（满足 FR-1.3），
保存时用 `domain/units.ts` 的 `parseAmount()` 解析成 `amount` / `unit` / `amountText` 三个字段
落库。UI 实时显示「识别为：500 g」让用户确认。

**理由**：
- 存储层仍然是结构化的（amount / unit / amountText 三段），后续换算与合并不受影响
- 录入体验从「想清楚再分两个框填」变成「照抄原文」，符合场景 A（从公众号复制菜谱）的操作习惯
- 解析不了的（如「两把」）整体落到 `amountText`，**不丢信息**，也不会被误当成数值参与计算

## D-006 · 2026-10-15 · 标签改名撞车时自动合并，而不是报错

**状态**：已决议（FR-2.10 / FR-2.11 的交互细节）

标签列表里的「改名」如果改成同维度已存在的名字，按字面执行会产生两个同名标签，
之后用户在筛选面板里根本分不清点的是哪个。

**决议**：改名时先查同维度是否有重名——有就直接走 `mergeTags`（关联迁移 + 原标签删除），
并提示「与已有『X』合并」。用户想表达的本来就是「这俩是一回事」，报错让他手动点两次合并是多余的。

跨维度不算撞车：`川菜`（菜系）与 `川菜`（口味）可以并存，因为它们是不同的筛选轴。

**副作用**：`createTag` 保持「同维度同名直接复用已有 id」的幂等语义，两条路径一致。

## D-007 · 2026-10-15 · 高级筛选用「草稿 + 应用」，不即时生效

**状态**：已决议（筛选面板交互）

筛选面板里每点一个标签都重查一次数据库，在数据量大时会明显卡顿，而且用户勾了 3 个标签
只是想表达「同时满足这三个」，中间态没有查询价值。

**决议**：面板内维护草稿状态，点「应用」才回写并触发查询；关闭面板不保存草稿。
已激活的筛选条件在列表页顶部以可点掉的 chip 展示，方便单条撤销。

## D-008 · 2026-10-15 · 解析结果里「食材名」统一落字典标准名

**状态**：已决议（对 FR-1.9 输出形态的明确）

规则引擎抽出来的食材，展示名直接用**内置字典的标准名**而不是原文名：
原文「排骨 500g」→ 存成 `name: 猪排骨, normalizedId: dict_xx`。

**理由**：详情页显示的食材名和备菜清单里合并用的键必须是同一个东西。如果详情页显示
「排骨」而清单里按「猪排骨」归并，用户会觉得系统在乱改他的菜。统一成标准名之后，
「为什么清单里出现了我没写过的『猪排骨』」这个问题就不存在了。

**代价**：用户输入「鸡腿肉」会被显示成字典里的规范写法。可接受——原文完整保留在
`sourceText` 里，随时能对照（FR-1.15）。

## D-009 · 2026-10-15 · LLM 出来的食材名一律在本地重算归一化

**状态**：已决议

模型返回的 `normalizedId` / `category` **一律丢弃**，保存前用内置字典重新跑一遍
`normalizeIngredient()`。

**理由**：这些 id 是本地 Dexie 的主键，模型无从知晓，它只会编。一旦采信，备菜清单的
合并就会静默错乱——而且是那种「看起来正常但数字不对」的错，最难发现。

同理，模型给的 `dimension` 也要校验是否在 `TagDimension` 枚举内，不然标签会挂到一个
筛选面板里根本不显示的维度上，凭空消失。

## D-010 · 2026-10-15 · .xlsx 用手写 ZIP 写入器，不引依赖

**状态**：已决议

FR-5.2 要求导出的表格有多个 Sheet，CSV 满足不了。引入 SheetJS（`xlsx`）会带来一个
约 700KB 的依赖，而这只是「把数组摊成表格」这一个用途。最终自己写了
`src/domain/zip.ts`（store 模式，约 100 行）和 `src/domain/xlsx.ts`（inlineStr 写法）。

**理由**：本项目是纯静态 PWA，首屏体积直接影响手机上的加载体验；而且 xlsx 的 open
packaging 规范稳定多年，需要的那一小部分不难写。用 inlineStr 省掉 sharedStrings.xml
又减掉一层复杂度。

**代价**：手写二进制格式出错时是「文件打不开」这种全有或全无的失败，没有库来兜底。
**因此**校验必须用独立实现，而不是自己的解析器验自己的写入器——测试里 `unzip -t`
验结构、Node 的 `Buffer` 验 base64 编码，都是这个考虑。

**未做的取舍**：不压缩（不实现 deflate），所以文件偏大。菜谱数据量很小（12 道菜
含 9 个 Sheet 约 46KB），换来的是零依赖 + 可审计。

## D-011 · 2026-10-15 · 图片先落库，菜谱后保存

**状态**：已决议

新建菜谱时还没有 `recipeId`，没法把封面挂在菜谱上。选图的瞬间就 `processImage` →
`putImage` 落进 `blobs` 表，拿到 `blobId` 暂存在表单里，保存菜谱时再用
`setRecipeCover` 挂上去。

**代价**：用户选了图又放弃保存，会留下一张没人引用的孤儿图。

**为什么仍然这么选**：另一条路是「必须先保存菜谱才能选封面」，这个流程很难解释，
而且用户常常是先看到一张图才想起要录这道菜。孤儿图的成本是可控的——进入
「备份与恢复」页时自动跑一次 `gcImages()` 回收，同时在界面上说明清理了多少。

**顺带定下的规则**：`setRecipeCover` 换图时，旧图只在**没有任何菜谱/步骤引用**时才删。
`purgeRecipe` 也做同样的事（先记下候选 id，删完引用再判断）。不这么做的话，
「清空回收站」会在库里留下一堆谁也看不见的图，白占配额——而这正好会踩中 FR-5.7 要提示的场景。

## D-012 · 2026-10-15 · 导入合并时冲突「保留较新的」，但设置项以备份为准

**状态**：已决议

`restoreAll(data, 'merge')` 对普通业务表按 `updatedAt` 比大小，只在新数据更晚时才覆盖本地；
`settings` 表例外——导入的一律生效，直接覆盖。

**理由**：业务数据的「新旧」有客观含义（用户在哪台设备上改的），取较新的是唯一说得通的规则。
但设置项没有 `updatedAt`（`AppSetting` 只有 `key` / `value`），硬套时间戳会让导入变成空操作，
用户会以为导入失败了。而且用户既然主动点了导入，就是想让备份里的设置生效——包括大模型配置。
这里顺着用户意图比猜时间更靠谱。

**另一个细节**：没有 `updatedAt` 的古老记录，在合并时一律视为「更旧」，不覆盖本地。
宁可少导入一条，也不要用一个来路不明的版本盖掉用户手上的数据。

## D-013 · 2026-10-15 · 备份里不含图片时也要能还原（覆盖模式除外）

**状态**：已决议

`dumpAll(includeImages=false)` 导出的文件里 `images: []`。用这种文件**覆盖导入**时，
图片引用（`coverBlobId` / `imageBlobId`）会指向不存在的 blob ——
`DishImage` 会退回占位色块，不会白屏，但图确实没了。

**为什么不拦**：FR-5.4 明确要求「可选择是否包含图片」，用户就是想导一个能直接看、
体积小的备份。真正危险的只有「覆盖导入」一种组合，这个风险在 UI 上说明——页面里写明
「JSON 是完整备份……请留这个」以及覆盖导入会清空当前数据。不做二次确认弹窗，
是因为用户在导入前已经看过说明、也选了模式。

**未做的取舍**：没有实现「导入时跳过缺失图片的引用并清理悬空 id」。占位色块是有效的
兜底显示，而多一条静默改写用户数据的逻辑，比一张能看出来的色块更糟。

## D-014 · 2026-10-15 · 时间线用一条可解释的贪心规则，不做调度优化器

**状态**：已决议

Q4 的决议是「最小形态，不做甘特图自动排程」。具体落到算法上是三条规则，按顺序应用：

1. **前置等待最长者先动**。每道菜算一个「起手等待」= 从第一步开始、到第一个需要动手的
   步骤之前累计的被动时长。等待长的（先腌、先发面）排前面。
2. **动手时间不重叠**。放置一道菜时，从小到大找第一个可行起点，使它的所有「动手步骤」
   都不与已放置的动手步骤重叠。**被动等待随便叠**——两道菜同时炖着完全没问题，
   同时炒两道才不行。
3. **空档 = 动手时段的补集**，长度 ≥ 3 分钟的列出来，提示「这 8 分钟只有排骨在炖」。

**为什么要用户看得懂，而不是更优**：这是一个做饭的人照着做的东西。规则如果复杂到无法用
一句中文说出来，用户遇到一次"为什么让我先做这个"就不会再用了。所以算法刻意保持贪心、
不回溯，宁可少省几分钟。

**刻意没做**：
- 不重排一道菜内部的步骤顺序（那等于改了菜谱本身）
- 不做「同一口锅只能同时炒一道」这类资源约束（模型复杂度和收益不成比例）
- 没标时长的步骤按 1 分钟估（`ACTIVE_STEP_SEC`）。这是个明说出来的近似，
  在页脚写清楚，而不是假装精确

**过程中被自己抓到的一个真 bug**：`findStart` 第一版只试 `0` 和各占用时段的 `end` 作为
候选起点，漏掉了「往左挪一点正好塞进空档」的位置。对「淘米 → 煮饭 → 盛饭」这种菜，
它会把整道菜排到炖菜结束之后，只省下 1 分钟；修成从约束
`T+o ≥ b.end` 或 `T+o+d ≤ b.start` 反解出**完整的候选点集合**（`{0} ∪ {b.end - o} ∪ {b.start - o - d}`），
同一道菜改成从第 1 分钟起手，省下约 1 小时。

## D-015 · 2026-10-15 · 计时器放全局 store，且用「目标时刻」而不是累加秒数

**状态**：已决议

两个决定都是被同一个场景逼出来的：**做菜时会来回切页面**。

**为什么是全局 store**：从制作模式跳去看备菜清单、或者切到另一道菜，计时器必须活着。
放在页面 state 里，一跳转就归零，那这个功能还不如手机自带秒表。

**为什么存 `endsAt` 而不是剩余秒数**：`setInterval` 累加在后台标签页会被节流
（浏览器把它降到 1 次/分钟甚至冻结），越跑越不准。改成每秒让 UI 重渲染一次、
用 `Date.now()` 与目标时刻比对，标签页被冻结几分钟回来时剩余时间依然是准的。
每秒 heartbeat 挂在 App 顶层，只有 App 卸载才停。

**到点提醒的取舍**：Web Audio 合成三声「叮」（880/1320 Hz 交替，不用音频文件）+
`navigator.vibrate` + Notification（有权限时）。三层里任何一层失效都不影响主流程，
因为真正兜底的是那条**必须手动点掉的红色横幅**——人可能正背对着手机切菜，
铃声过了没看见就永远不知道时间到了，所以到点的计时器不自动消失。

## D-016 · 2026-10-15 · 计时器条的占位高度两侧共用同一个函数

**状态**：已决议

计时器条浮在屏幕底部，会盖住页面最后一块内容——在制作模式里那块正好是「下一步」按钮。
所以页面底部必须留出与它等高的空白。

**为什么把高度算成函数**（`src/domain/timerLayout.ts`）：如果 TimerBar 里改了行高、
App 里的留白没跟着改，就会出现「在某些手机上按钮被挡住」这种只在特定设备复现的 bug。
两边都只读 `timerBarHeight()` 与同一组常量，数字只在一处定义，并有 7 个用例锁住数学。

**为什么已响铃的计时器不单独占行**：它们被折叠进那一条红色横幅里，所以行数只数未响铃的。
不这么做的话，两个计时器同时到点会凭空多留两行空白。同理「全部取消」小按钮只在
「没有横幅且两个以上在跑」时出现——这个条件在 TimerBar 与 `timerBarHeight` 里必须一致，
注释里写明了。

## D-017 · 2026-10-15 · 「这一顿的感受」存进制作历史，不额外写一条笔记

**状态**：已决议

收工时用户会填「打个分 + 记一句感受」（FR-3.31）。这句话如果同时写进
`cookHistory.note` 和一条 `Note` 记录，菜谱详情页会把同一句话显示两遍。

**决定**：感受只落 `cookHistory.note`；制作过程中的随手笔记（FR-3.26）走已有的
`addNote()`。两者在详情页是分开的两块——「这一顿怎么样」和「这道菜要怎么做」。

**另一个一致的取舍**：收工不做「这道菜已经在今日菜单里就合并」之类的聪明事。
`finishCooking` 只做三件事，且**在同一个事务里**：菜单项置为已完成、写一条历史、
菜谱的 `cookCount + 1` 并重算平均分。这三个数字用户都会在界面上看到，
任何一个落后于其他两个都是那种"说不上哪里不对但就是不对劲"的 bug。

**平均分只统计打过分的次数**：不打分的收工不写 `rating`，也不当成 0 分参与平均——
否则用户越做分越低。

## D-018 · 2026-10-15 · 加一条「Opacity 修饰符必须是 5 的倍数」的源码检查

**状态**：已决议

**背景（真实踩到的坑）**：Tailwind 的颜色透明度修饰符只认 5 的倍数
（默认 opacity scale 是 0、5、10…100）。计时器条的行原本写 `bg-stone-900/92`，
构建成功、类型检查通过、测试全绿，但编译出的 CSS 里**根本没有这条规则**——
Tailwind 遇到不认识的值既不报错也不警告，直接什么都不生成。结果是深色的计时器条
变成了透明背景，白字浮在页面内容上，几乎看不清。

这是"全绿但坏了"的典型：没有任何一层会告诉你有问题。我是把编译产物里的类名逐个对
一遍才发现的（用一个临时文件同时写 `/90` `/92` `/95` `/55` 编译后看谁生成了 CSS）。

**决定**：加 `src/styles.test.ts`，扫 `src/**/*.ts{,x}` 里所有 `颜色/NN` 写法，
凡 NN 不是 5 的倍数就失败，并在报错信息里给出改法（改成 5 的倍数 /
用 `/[0.92]` 任意值写法 / 加进 `theme.extend.opacity`）。

**验证过它不是空跑**：把 `TimerBar.tsx` 的 `/90` 改回 `/92`，测试确实红，
报出 `src/components/TimerBar.tsx: bg-stone-900/92`；改回去就绿。
（文件里的反例用字符串拼接写，否则这个检查会把自己的注释也判为违规。）

**顺带确认没问题的写法**：`bg-black/55`、`bg-stone-50/95` 都是 5 的倍数，能正常生成；
`src/index.css` 里 `@apply ... focus:ring-brand-500/20` 也正常（`@apply` 展开成
`--tw-ring-color`，本来就不会在产物里留下类名，别被 grep 不到误导）。
